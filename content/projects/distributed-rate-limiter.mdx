## The Problem

Every rate limiter I'd used at work fell into one of two categories: local (fast but useless in a multi-node environment) or distributed (correct but adding 5-20ms to every request via a Redis round-trip).

I wanted both. This is the design that got me there.

## Architecture

The key insight: use a **local sliding window** as a fast path, synced asynchronously to Redis. Most requests never touch the network.

```
Request → Local bucket check → ALLOW (fast path, ~0.1ms)
                            ↓ (if near limit)
                        Redis sync → ALLOW/DENY (slow path, ~2ms)
```

Local state is a token bucket per key, stored in a sharded in-process map. Redis holds the authoritative count. Sync happens on two triggers:
1. When local count crosses a configurable threshold (e.g. 80% of limit)
2. Every 100ms via a background goroutine

## Trade-offs

This approach accepts **brief over-counting** at bucket boundaries. Two nodes can both see "3 tokens remaining" simultaneously and both grant a request, briefly exceeding the limit. In practice, with a threshold at 80%, overage is bounded to ~20% of the limit window.

For most use cases — preventing abuse, protecting downstream services — this is a fine trade. For billing-critical rate limits, you'd want the strong consistency of a Lua script on Redis.

## Numbers

| Scenario | P50 | P99 |
|---|---|---|
| Fast path (local) | 0.08ms | 0.3ms |
| Slow path (Redis sync) | 1.9ms | 4.1ms |
| Baseline (pure Redis) | 2.1ms | 12ms |

Benchmarked on a 3-node cluster, 50k req/s aggregate.
