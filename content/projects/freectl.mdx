## The Problem

We were managing a multi-cluster Kubernetes platform with Helm for templating and a GitOps flow on top. 
We deliberately adopted hydrated manifests — a practice I arrived at through experience and seen advocated 
by some of the main contributors to ArgoCD: you render your Helm templates into plain YAML and commit the 
result to git, so your GitOps controller applies raw YAML rather than running Helm at deploy time. This
removes a dependency on the helm binary from your GitOps tool (e.g. ArgoCD), and has the added benefit of
PRs being more auditable on exactly what is going to change.

The downside at scale is duplication. When you have multiple clusters with similar but not identical 
configurations, you end up committing variations of the same YAML across many directories. Values files 
diverge for simple reasons such as the example below:

``` yaml
karpenter:
    settings:
        clusterName: nightingale
```

The other problem I hit shortly after going to production: hydrating all the Helm charts in a bash 
loop — one `helm template` call per chart per cluster, sequentially — took over two minutes for a full 
re-render. Seeing as we use pre-commit hooks to ensure everything is correctly rendered, two minutes is
not acceptable for this use case. I can do better.

## What freectl Does

`freectl` is a Go CLI I built with [Cobra](https://github.com/spf13/cobra) (very common cli framework in Go)
that was intended to replace all the bash scripts we were leveraging heavily for the main development loop.

The first thing it solved was speed. Running all Helm renders concurrently with goroutines brought the 
full hydration from over two minutes to under ten seconds, which is fast enough to keep me from context 
switching :)

It then grew into the primary operational interface for the platform:

**Manifest hydration** — `freectl hydrate` walks the repo layout and runs `helm template` for every 
application across all clusters concurrently, writing each app's output to a committed 
`resources/output.yaml`.

**Cluster bootstrapping** — `freectl bootstrap run` bootstraps a fresh cluster through a strict, 
ordered pipeline: CRDs first, then namespaces, then CNI (Cilium replaces the AWS VPC CNI), then 
addons via a configurable step list. Each phase waits on rollout readiness before advancing. 

**Tenant generation** — `freectl mint` reads team YAML files describing a team's namespaces and 
generates the corresponding Kubernetes resources into `_autogenerated/` directories within the 
correct cluster layout. Tenant onboarding that previously required direct platform team 
involvement became self-serve: fill in the spec, run `mint`, commit the diff.

**Template variable substitution** — Values files support `${CLUSTER_NAME}`, `${ACCOUNT_ID}`, 
`${REGION}`, and similar variables that get resolved before `helm template` runs. Common config 
is defined once in `.freectl.yaml` and referenced everywhere. This eliminated most of the 
copy-paste that hydrated manifests normally create at multi-cluster scale, without breaking the 
explicit-state property that made the pattern worth using.

## Honest Assessment

freectl is overfit to the internal environment — the interfaces are more opinionated than they 
need to be, and extending it for a meaningfully different setup would take more work than I'd 
want to ask of someone picking it up cold. The bootstrapping and minting features in particular 
added scope that pushed the tool into doing more than one tool probably should.

The outcomes were good. Engineers have a fast, well-documented interface for day-to-day platform 
operations, and tenant onboarding that previously required direct platform team involvement can 
largely be self-served. If I were building it again I'd think harder about the extension points 
earlier, so the interface was clean enough to be genuinely useful outside the context it was 
built for. Plus I have always wanted to open source something useful :D
