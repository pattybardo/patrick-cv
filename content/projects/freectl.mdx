## The Problem

We were managing a multi-cluster Kubernetes platform with Helm for templating and a GitOps flow on top. The pattern that naturally emerges here is hydrated manifests: you render your Helm templates into plain YAML and commit the result to git, so your GitOps controller applies raw YAML rather than running Helm at deploy time. This keeps the applied state explicit and auditable.

The downside at scale is duplication. When you have multiple clusters with similar but not identical configurations, you end up committing variations of the same YAML across many directories. Values files diverge. A config change that should be one line becomes a sprawl of similar-but-different files across the repo.

The other problem I hit immediately: hydrating all the Helm charts in a bash loop — one `helm template` call per chart per cluster, sequentially — took over two minutes for a full re-render. Pre-commit hooks that take two minutes don't stay as pre-commit hooks for long.

## What freectl Does

`freectl` is a Go CLI built with [Cobra](https://github.com/spf13/cobra) that replaced the bash loop and kept growing from there.

The first thing it solved was speed. Running all Helm renders concurrently with goroutines brought the full hydration from over two minutes to under ten seconds, which is fast enough to keep me from context switching :)

It then grew into the primary operational interface for the platform:

**Manifest hydration** — `freectl hydrate` walks the repo layout and runs `helm template` for every application across all clusters concurrently, writing each app's output to a committed `resources/output.yaml`. With `--check` it diffs instead of writing — the pre-commit hook runs in check mode so engineers know exactly what changed before it lands in git.

**Cluster bootstrapping** — `freectl bootstrap run` stands up a fresh cluster through a strict, ordered pipeline: CRDs first, then namespaces, then CNI (Cilium replaces the AWS VPC CNI), then addons via a configurable step list. Each phase waits on rollout readiness before advancing. `freectl bootstrap validate` runs the preflight checks in isolation — identity and account verification, helm drift detection — without touching the cluster.

**Tenant generation** — `freectl mint` reads team YAML files describing a team's namespaces and generates the corresponding Kubernetes resources into `_autogenerated/` directories within the correct cluster layout. Tenant onboarding that previously required direct platform team involvement became self-serve: fill in the spec, run `mint`, commit the diff.

**Template variable substitution** — Values files support `${CLUSTER_NAME}`, `${ACCOUNT_ID}`, `${REGION}`, and similar variables that get resolved before `helm template` runs. Common config is defined once in `.freectl.yaml` and referenced everywhere. This eliminated most of the copy-paste that hydrated manifests normally create at multi-cluster scale, without breaking the explicit-state property that made the pattern worth using.

## Honest Assessment

freectl is overfit to the internal environment — the interfaces are more opinionated than they need to be, and extending it for a meaningfully different setup would take more work than I'd want to ask of someone picking it up cold. The bootstrapping and minting features in particular added scope that pushed the tool into doing more than one tool probably should.

The outcomes were good. Engineers have a fast, well-documented interface for day-to-day platform operations, and tenant onboarding that previously required direct platform team involvement can largely be self-served. If I were building it again I'd think harder about the extension points earlier, so the interface was clean enough to be genuinely useful outside the context it was built for.
