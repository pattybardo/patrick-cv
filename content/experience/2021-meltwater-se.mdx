## What I Worked On

This was my first proper software job. I joined the team that owned Meltwater's search platform — a big Elasticsearch cluster plus the APIs other teams used to store and search documents in it. Media intelligence means tracking what's being said across news, social, and broadcast, so the cluster takes a lot of writes and serves a lot of unpredictable queries from thousands of customers.

I spent most of my first stretch on the upgrade from Elasticsearch 1.7 to 7.x.

## The Migration

1.7 was years past end-of-life and had collected a lot of debt. Jumping six major versions isn't an upgrade you can do in place — the query DSL had changed, mapping types were gone, and the on-disk formats weren't compatible. So we ran two clusters side by side and cut over:

1. **Shadow indexing** — write new documents to both the old and new cluster
2. **Backfill** — replay the existing corpus into the new cluster and check document counts and query results against the old one
3. **Compatibility shim** — a thin translation layer so the application tier could keep using the old query patterns while we updated them one at a time
4. **Cut-over** — move read traffic over with a fast path back if something looked wrong

It went out without a customer-facing incident, which for a migration of that size is most of what you're hoping for. The new cluster also handled nested aggregations and higher concurrent query loads that the old one couldn't.

## Shard Distribution

The more interesting work was on hotspots. Elasticsearch decides where to put shards based mostly on keeping the shard *count* roughly even across nodes, which quietly assumes every shard does about the same amount of work. Ours didn't. Some shards were getting hammered and others sat idle, so a handful of nodes would redline while the rest coasted — and that's where the indexing lag and the 2am pages came from.

A previous intern project had already built a load-driven optimiser for this: estimate the actual load per shard from Prometheus, then move shards around to even out the load per node instead of the count. It used Mean Squared Error against the average node load to decide whether a move helped. I picked that system up and made a couple of changes that mattered.

First, I swapped the error function. MSE was fine, but I wanted something that punished a node sitting far from the mean more harshly than MSE did, so the optimiser would prioritise pulling down the genuinely overloaded nodes rather than nibbling at small imbalances everywhere. That alone gave us flatter load distributions.

Second, I added a disk step. Load and disk usage can't both be optimised at once — moving a shard to balance load can wreck your disk balance and vice versa. So I had it check the disk MSE across nodes first: if that was above a threshold, run a disk-balancing pass before the load pass. The obvious benefit was better disk distribution. The less obvious one turned out to be the bigger win — the disk pass shuffles the hot shards into a new arrangement, and because shard placement is boxed in by hard constraints (primaries and replicas can't share a node, replicas have to sit in different availability zones), a fresh starting topology sometimes let the load optimiser reach a *lower* minimum than it could from where it started. You're effectively giving it a different basin to descend into.

The combined effect was that we could index more for the same hardware — around 200k documents per second on a cluster that wasn't much bigger than before, without throwing nodes at the problem the way the original incident response had.

## Observability

A petabyte-scale cluster needs decent monitoring to run safely, so I worked on the alerting around shard health, JVM garbage collection, search latency percentiles, and indexing throughput — enough to catch degradation before customers felt it. Being on-call for it every six weeks was a fast way to learn which of those signals actually mattered.
