## The Work

I joined Zenseact as a Senior Software Engineer on the Bazel and CI ecosystem team. The focus was a large Bazel monorepo building the software stack for autonomous vehicles, and the work was about finding concrete bottlenecks and removing them — not designing systems in the abstract, but getting close to the actual friction engineers were hitting every day.

## Testing What You Can't Test Before You Ship

One recurring problem with large build systems is that some changes can't be meaningfully validated before they land. If you're upgrading Bazel itself, your CI pipeline runs on the old version. Pre-merge testing against the new version doesn't exist yet — there's structurally nothing to test against.

I designed a post-merge validation pattern using branches to handle this class of problem. Rather than trying to force pre-merge coverage where it can't work, a designated branch tracks the environmental change and CI validates against it post-merge, before it reaches the broader fleet. The pattern is reusable: I first applied it to the Bazel version upgrade, but it works for any environmental change where the testing infrastructure itself is what's being changed.

## Dark Builds

We had a dependency on a pre-built baseline from our parent company — a large artifact that Zenseact's software layered on top of. When an engineer needed to validate a patch against a different version of that baseline (the typical use case: proving a fix in the parent company's code resolved a bug we were seeing downstream), the only option was to do it entirely locally. Ad-hoc rebuilds, uncommitted patches, results nobody else could reproduce or review.

I built a CLI-driven dark build workflow that brought this into the normal SDLC. Engineers trigger a baseline rebuild through a command, everything runs through CI on a branch, and the patches are committed and reviewable. It turned a process nobody could trace into one with a proper audit trail.

## BuildBuddy

I set up a self-hosted BuildBuddy instance to give developers timing visibility into their Bazel builds in CI. Low implementation effort — a Friday afternoon, really — but the org-wide view of where build time was actually going was useful both for identifying what was worth optimising and for helping engineers understand why their specific changes were slow.
